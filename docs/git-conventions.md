# Git-соглашения

Читать перед созданием ветки, коммита или Pull Request.

## GitHub Flow

- `main` — всегда рабочая, деплоимая ветка. Прямые коммиты в `main` не делаем.
- Каждая новая задача — отдельная ветка от актуального `main`. Именование: `feature/<название>` для фич, `fix/<название>` для багфиксов (kebab-case, например `feature/main-screen`).
- Изменения вливаются в `main` через Pull Request после ревью; ветку после merge удаляем.

## Соглашение о коммитах

Используем **Conventional Commits**: `type(scope): описание`.

- **type** — `feat` (новая функциональность), `fix` (багфикс), `refactor`, `docs`, `chore`, `test`, `style`.
- **scope** — затронутый пакет: `backend`, `frontend`, `shared` (можно опустить, если изменение общее для монорепо).
- **описание** — в повелительном наклонении, с маленькой буквы, на русском, без точки в конце.

Примеры из истории репозитория:

```
feat(backend): модуль учёта транзакций (доходы/расходы) на CQRS
feat(frontend): главный экран с меню, списком транзакций и созданием
fix(backend): rate limiting, ограничение CORS и удаление мёртвой модели Expense
refactor(backend): перевод модуля categories на CQRS
```

При создании коммитов НЕ добавлять строку `Co-Authored-By: Claude ...` в сообщение коммита — это личный репозиторий, и такой trailer добавляет Claude в GitHub Contributors, что нежелательно.
